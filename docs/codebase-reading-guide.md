# ChatDKU upstream codebase reading guide

Upstream: https://github.com/Edge-Intelligence-Lab/ChatDKU-Open-Source (main, inspected October 2026). The candidate code in this repository is an **independent, smaller implementation**. It is not a fork, patch, or deployed component of upstream. The supplied production overview is a third, separate architecture. This distinction matters when presenting the work.

## Start at the Agent-Only path

| Read in this order | What to trace |
| --- | --- |
| `README_EN.md`, `Documentations/Agent-Only-Quick-Start_ZH.md` | The intended CLI mode, required services, and setup steps. |
| `docker-compose.agent.yml` | Agent, Redis, ChromaDB, and external model/embedding endpoints. |
| `chatdku/chatdku/core/agent.py` | `main()` calls `setup()`, configures a DSPy LM, constructs `Agent`, and handles a CLI question. `Agent.forward()` drives planning, retrieval, judging, optional query rewrite, and synthesis. |
| `chatdku/chatdku/core/dspy_classes/plan.py`, `judge.py`, `query_rewrite.py`, `synthesizer.py` | DSPy signatures and the decisions at each step. |
| `chatdku/chatdku/core/tools/llama_index.py` | `DocRetrieverOuter()` wraps vector and keyword tools and passes returned passages to the agent. |
| `chatdku/chatdku/core/tools/retriever/{vector_retriever,keyword_retriever,reranker}.py` | ChromaDB/TEI semantic retrieval, Redis BM25 retrieval, and reranking. |
| `chatdku/chatdku/ingestion/{update_data,load_chroma,load_redis}.py` | How documents become searchable records. |

The CLI command from the current repository root is `docker compose -f docker-compose.agent.yml exec agent python -m chatdku.core.agent` after the services and document indexes have been prepared. The quick-start's clone line points to an older repository name, so clone the upstream URL above. Never copy a committed `.env` into a public candidate submission; configure secrets locally.

## How a question travels through upstream

1. The module-level `main()` configures the LM and opens the command-line loop. `Agent.forward()` receives `current_user_message`, `user_id`, `search_mode`, and optional `files`.
2. `Planner` creates DSPy tool calls. The exposed `DocumentRetriever` accepts `semantic_query` and optional `keyword_query`.
3. `DocRetrieverOuter` calls `VectorRetriever` on ChromaDB via the embedding server, and `KeywordRetriever` on Redis. Each returns `NodeWithScore` data with text and metadata. Optional reranking reduces candidates.
4. Retrieved content goes into `ToolMemory`. `Judge` can ask for another iteration; `QueryRewrite` can revise the query. The CLI currently constructs `Agent(max_iterations=1)`, so the default CLI example does not exercise a second search round even though the class supports it.
5. `Synthesizer` receives the question, conversation/tool history and instructions for a reference list with document name, URL, and page. Its citations are generated by the model from text; evaluate whether each cited page actually supports its claim.

Two useful details to verify experimentally: vector results expose `file_name`, whereas keyword results expose `filename`; and the keyword retriever tokenizes with English NLTK resources. These are code-reading observations, **not measured bugs**. They suggest tests for consistent metadata normalization and Chinese retrieval. Inspect the exact ingestion output and downstream handling before proposing a change to upstream.

## Candidate prototype versus upstream

| Concern | Upstream open-source implementation | This candidate prototype |
| --- | --- | --- |
| Search storage | ChromaDB + Redis and external TEI | In-memory passages, sentence-transformer vectors, local BM25 |
| Agent | Planner, tool memory, Judge, query rewrite, Synthesizer | One plan, two retrieval tools, rank fusion, synthesis |
| Citation | Synthesizer prompt requests source list | Program validates selected evidence IDs and renders document/page metadata; claim support is still unverified |
| Scope | CLI plus broader web/backend services | CLI mini pipeline and benchmark harness |

The prototype is a small experimental baseline for discussing design choices. To turn it into a contribution **based on upstream code**, fork upstream, work on a feature branch, adapt and test a focused change in its actual module, then report the upstream commit, diff, commands, and observed result. Do not describe the current independent repository as such a contribution.

## Reproduction boundaries

The upstream Agent-Only setup needs Docker, a local OpenAI-compatible LM server, a TEI embedding server, Redis, ChromaDB, and indexed documents. The current execution environment has no GPU/model server and cannot demonstrate that path. The candidate prototype's locally checked keyword baseline does not establish upstream performance or answer quality. Use the *same authorized document corpus and labeled bilingual question set* for comparisons, and log each configuration separately.
